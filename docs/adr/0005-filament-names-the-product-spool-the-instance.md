# Filament names the product, Spool names the physical instance

The vault used one note type, tagged `3dprint/filament`, for both a filament product and
a physical spool of it. A single note carried `material`, `color`, `brand` and
`product-line`, which describe a product, alongside `spool-id`, `purchase-date`,
`gross-weight` and `lot-code`, which describe one spool. A `usage` note's `filament` key
therefore named a product and pointed at an instance. We have split them: **Filament** is
the product, **Spool** is one physical spool of that product and links to its Filament,
and `usage` references the Spool.

The split also aligns the vocabulary with Spoolman, which is being introduced alongside
this service and which models Vendor -> Filament -> Spool with the same meanings. Using
"filament" for a physical spool in one system and for a product in the other would have
meant translating between them in the operator's head on every lookup.

## Considered Options

A pure rename -- calling the existing note type Spool and leaving product attributes on it
-- was the alternative, and it fixes the immediate ambiguity for the cost of one tag and
one filename change. It was rejected because the product attributes would stay duplicated
across every spool of the same product, which is already visible in the vault as
`temp-range-°C` repeated across dozens of notes, and because Spoolman will impose the
product/instance distinction regardless.

The timing argued for doing it now rather than later. The migration tool that converts
~680 legacy notes (ADR 0001) is not yet written, so this split rides along in a diff that
was going to be reviewed anyway. Deferring it means a second migration over a larger
corpus.

Introducing Vendor as a third entity, which is what Spoolman does, was rejected. `brand`
stays a string on Filament. The alignment argument only applies where a mismatch causes
translation errors, and brand-as-string does not; two new note types in one migration is
already the limit of what can be reviewed in one pass.

## Consequences

The tag `3dprint/filament` changes meaning: it tagged 97 physical spools and will tag
product types. Every existing query over it keeps running and starts returning different
things, including the Dataview blocks embedded in the spool notes themselves and anything
under `bases/`. This is the one part of the change that fails silently, so auditing those
references is a named step of the migration rather than something to notice later.

Filament notes are generated by the migration, by grouping the existing spool notes on
(brand, material, colour, product-line) and emitting one per distinct tuple. This
deduplicates facts already recorded rather than inventing any, but near-duplicate
spellings will produce spurious separate types, so the operator reviews the generated list
before it is written.

Spoolman keeps net weight in both places -- as a type default and as a per-spool value
that shadows it -- and the vault follows: `nominal-weight-grams` sits on Filament with an
optional Spool override, which is what the same product sold in 1 kg and 250 g requires.
